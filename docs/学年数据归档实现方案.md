# 一、背景与目标

**结论**：当前工作台**不具备按学年区分数据的能力**，也不存在归档概念。本方案不新增程序行为，而是定义「学年」成为一级建模对象后，系统必须具备的能力与不可逾越的约束；目标是把「多批次结构存在但学年不可见、重来即整包替换」升级为「按学年整体封存、历史只读可查、当前学年写入与归档副本隔离、封存不可变且可留痕勘误」。

## 1.2 目标

1. 引入**学年实体**，一学年下挂多批次（分学期、补评、专项评定），归档按**学年整体**封存。
2. 生成**全量可复现快照**，脱离当前工作数据仍可独立复盘与复核。
3. 管理员工作台内**全量只读**查询历史学年；学生端仅可查**本人历年已公示结果**。
4. 归档快照**不可变**；更正只以独立**勘误追加记录**留痕，原始快照永不改写。
5. 新学年**仅继承配置与结构模板**，业务数据全空。
6. 归档副本与当前工作学年**隔离**，当前学年任何写操作不得触碰归档副本；支持整学年导出/恢复迁移，跨设备同步明确学年边界。

## 1.3 非目标与本期边界

- 不实现「申请 / 审核 / 审批」实体，不改造八层评定算法与名额规则。
- 不假设具体技术栈、存储方案、框架或部署形态；不给出编码步骤。
- 不改动既有仓库文件与业务数据。
- 归档能力的实施排期、是否及如何落地到单文件应用，另行确认。

## 1.5 关键成功判据

任一时点须同时成立：**当前学年可写、历史学年只读、归档副本不被任何当前学年写操作触碰、任一历史结果可脱离当前数据独立复核**。

# 二、归档边界

**结论**：归档对象 = 学年实体（含其下全部批次）；归档产物 = 一份自包含、不可变、带清单与指纹的全量快照。边界必须同时写清「归档什么」「不归档什么」，以及「申请/审核缺失时用什么替代」。

## 2.1 归档对象与学年实体最小属性

- 学年属性：`yearId`（稳定唯一内部标识，不以显示名为键）、显示名、起止日期（选填）、`status`、`batchIds[]`、`archivedAt` / `archivedBy`（操作者与留痕）、`snapshotFingerprint`、`manifest`（归档清单）、`archiveSchemaVersion`、勘误指针与计数；顶层需有「当前学年」上下文标识。
- 学年状态：`未开评 → 评定中 → 归档中 → 已归档`（可选「已作废」）。**学年状态与各层 `layerState` 五态属两个层次，不得混淆。**
- 批次归属：批次侧仅新增归属字段，**不改动** `id / name / students / detail / todos / quota / stage / publications / objections` 等现有字段语义；`activeBatch` 与 `B()` 的现有取批次行为保持兼容。存量批次（如 `b1`）平滑归入一个默认当前学年，保证历史数据仍可见。
- 一学年下挂多批次；批次归属单一学年，不允许跨学年。学年整体归档，不允许只归档其中部分批次。

## 2.2 需归档的数据范围（按实际系统取舍）

| 类别 | 归档内容 |
|---|---|
| 学年与批次结构 | 学年实体全部属性；每批次的 `id / name / isDemo / createdAt / mtime` 与归属 |
| 参评基础数据 | `students`（16 项字段，学号为主键）、`detail`（15 列附加分明细，含「测评学年/测评学期」两列） |
| 名额 | `quota` 名额分配表 |
| 评定过程与结果 | `stage.l1~l8` 每层 `versions[]`（**含未确认的中间试算版本**）与 `activeVid`；每版本的 `vid/at/by/confirmedAt/confirmBy/summary/data/baseRefs/dataHash/diff/lock/switchLog/recount` |
| 引用与差异链 | `baseRefs` 上游引用固化、`diffs`、`switchLog`、`mainFrom` 等可复盘引用信息 |
| 口径与规则 | `rankWeights / gradeRules / sanhaoRules / ganbuRules / xingzhiRules`、`followPolicy`、`flags`、`schemaVersion`、字段口径定义（基础字段表、明细列定义、公示层定义）、`audit` |
| 公示 | `publications[]` 全字段（层级、版本、列、标题、起止、状态、短链标识、表单链接、说明、时间戳） |
| 异议 | `objections[]` 全字段（关联公示、层级、学号姓名、内容、状态、回复、来源、时间戳） |
| 待办与留痕 | `todos`、各类 `mtime / __mtime`、审计与操作留痕 |
| 归档元数据 | 归档时刻、操作者、原因、清单计数与指纹、归档结构版本、归档时刻勘误计数（应为 0） |

**完整性定义**：「全量可复现」= 脱离当前工作数据，仅凭归档副本即可重放清单计数、各版本结果与指纹、公示/异议/审计与关键结果，且与归档时刻记录一致；副本须自带规则配置与字段口径，不依赖当前 state 的其它部分。

## 2.3 明确不归档

- 程序与代码本身（由 Git 提交与 `vX.Y.Z` 标签追溯，见 `README.md:69-73`）。
- 运行态临时数据：内存筛选/搜索词、打开的视图与弹窗、临时计算变量、UI 折叠状态。
- 同步凭据：Token、同步码等设备级密钥，**不得进入任何归档副本或导出文件**。
- 用户偏好与设备配置（默认排除，待确认）：星标工具、角色选择器态、自定义公示接口地址。
- 外部云资源本体（云端短链内容、Gist 同步文件）——其留存策略单列待确认。
- 勘误记录本体：作为独立追加记录存在，不并入原始快照。
- 空占位、未来学年、备份 JSON 文件本身。

## 2.4 申请/审核缺口的替代证据链

系统不存在申请单、审核单与审批记录；`detail` 中的「申请项名称」仅是附加分明细的一个数据列，与申请流程无关。历史可复盘性由以下**替代证据链**承担，归档必须完整保留：

> 数据导入/补齐（`students` + `detail`）→ 八层计算与版本留存（`baseRefs` 引用固化、`dataHash`、diff）→ 选定使用版本/确认（`confirmedAt` / `confirmBy`）→ 公示单（起止、列、状态、短链）→ 异议登记/回复/采纳/不成立 → 审计留痕（`switchLog` / `audit` / 时间戳）。

## 2.5 归档产物

自包含、不可变、带归档清单与整体指纹；清单逐类记录计数与指纹（含每层版本数、其中试算版本数）；归档前须冻结源、生成副本并做**回放一致性校验**，通过后方可提交为「已归档」。

# 三、功能要求

**结论**：以下 FR1~FR10 描述能力、规则、状态与约束，不涉及实现手段。

| 编号 | 能力 | 关键规则与状态 |
|---|---|---|
| FR1 | 学年建模与批次归属 | 一学年下挂多批次；批次新增归属但不改语义；学年状态机；标识与显示名解耦；存量数据平滑迁移 |
| FR2 | 双上下文与切换 | 显式区分「当前学年（可写）」与「历史学年（只读）」；提供可用的历史学年入口（不得依赖现状失效的批次选择器）；切换只改变上下文与可用操作集，不改变数据 |
| FR3 | 归档触发与前置校验 | 管理员手动触发「结束本学年并归档」；校验全通过方可进入，否则**整体阻断并逐条给出原因** |
| FR4 | 快照生成与完整性 | 冻结源 → 生成清单（逐类计数 + 指纹）→ 生成自包含副本 → 回放一致性校验 → 通过才提交 |
| FR5 | 封存不可变 + 勘误 | 快照只读、永不改写；更正仅追加独立勘误记录；查询显式标注；勘误不影响归档指纹 |
| FR6 | 历史可见性 | 管理员台内全量只读；学生端仅本人历年已公示结果；其它角色范围待确认 |
| FR7 | 新学年基线 | 仅继承配置与结构模板；业务数据全空；独立 `yearId` |
| FR8 | 导出/恢复/迁移/同步边界 | 整学年导出为自包含归档文件、按学年恢复迁移；导入恢复须按学年边界判定，不得覆盖归档学年；云同步载荷明确学年边界 |
| FR9 | 异常与一致性 | 重复归档幂等、部分失败原子性/可重试/不留半成品/失败可见、并发中断与中途写入处理 |
| FR10 | 写入拦截覆盖 | 逐一覆盖 3.4 节全部覆盖点；历史上下文下所有写路径统一「拒绝 + 原因 + 留痕」 |

## 3.1 归档触发节点与前置校验清单

**触发节点**：本学年评定周期结束、结果定稿且公示结束后，由管理员显式执行「结束本学年并归档」。此外，「新建/切换到新学年」前须存在学年门禁：上一学年应为「已归档」，或明确标注为未归档并阻止其继续写入，避免多学年并行可写。

| 校验项 | 判定口径 | 阻断原因 |
|---|---|---|
| 学年状态 | 必须为「评定中」 | 未开评/归档中/已归档不得触发 |
| 批次归属 | 下挂批次 ≥1 且归属完整 | 存在孤儿批次 |
| 结果确认 | 所有参评层 `activeVid` 存在且 `confirmedAt` 非空，处于 `confirmed` / `published` | 存在未计算或未确认层（逐层列出） |
| 公示结束 | 无「公示中」公示单；对外公示单均为「已结束」；「已撤销」须清理或明确标注 | 公示仍在进行 |
| 异议闭环 | 不存在未终结异议（见 3.2） | 异议未闭环（逐条列出） |
| 结果已锁定 | **不以 `v.lock.lockedAt` 判定**（该字段全库无赋值点，恒为 `null`）；定义为「全层已确认 + 归档二次确认 + 归档完成即赋予封存冻结态」 | 结果未冻结 |
| 配置齐备 | 规则配置、名额、字段口径版本已记录且可读 | 缺少复盘口径 |
| 完整性自检 | 清单计数与指纹一致、无未落盘写入 | 数据不一致 |
| 二次确认与留痕 | 操作者/时间/原因写入审计 | 缺少归档凭证 |

**触发后果**：学年状态 `评定中 → 归档中 → 已归档`；生成不可变快照并固化指纹与清单；写入归档审计；当前学年上下文按 3.5 准备。任一校验不通过则整体阻断、不产生半成品、逐条列出原因。

## 3.2 口径定义（避免照搬未完成能力）

- **异议闭环**：现状状态为「待核实 / 已回复 / 采纳-待重算 / 不成立」，且**无显式闭环终态**（采纳后只引导重算，不回写终结）。默认采用组合判定：待核实、已回复但无终结结论、采纳-待重算 均视为未终结；「不成立」视为闭环；采纳类须可追溯到「重算 → 重新确认 → 重新公示 → 公示结束」。是否新增显式终态列为待确认。
- **结果已锁定**：现状 `lock.lockedAt` 仅有读取与结构预留、无写入实现（`index.html:1042,1090,1208,1452`），界面「已确认锁定」实际对应 `confirmedAt`。归档不得依赖该字段，改用归档封存态表达。
- **全量含试算版本**：归档以「归档时刻已存在的全部版本」为准；归档前禁止触发版本回收（保留最近 N 个版本策略）与上游切换清空下游，否则「全量」不成立；归档副本自身永不参与版本回收。

## 3.3 可见性矩阵

| 使用者 | 当前学年 | 历史学年 | 约束 |
|---|---|---|---|
| 管理员（现状唯一角色） | 全部读写入口按现状可用 | 工作台内**全量只读**：名单、明细、名额、八层全部版本（含试算）、公示单、异议、配置、审计、归档清单与勘误链 | 只读由写入拦截保证，非仅界面置灰 |
| 学生（公示链接访问者） | 凭学号+姓名查本人已公示结果 | 凭学号+姓名查**本人历年已公示结果**，结果带学年标识与勘误标注 | 强制「仅本人 + 仅已公示」过滤；不得返回他人数据 |
| 辅导员 / 评审委员 | 文档矩阵未落地，代码无该角色 | 不开放历史查询入口（默认） | 权限范围待确认 |

## 3.4 隔离约束（核心）

以「**双上下文 + 全量路径排除 + 写路径统一拒绝**」三件套表达：

1. 归档副本**不得位于被 `save()` 全量覆盖的可变 state 内，也不得参与按批次 id 并集的云同步合并路径**——这是「归档副本不被当前学年写操作触碰」的根本边界。
2. 归档内批次名、版本号、公示展示名、学年显示名均固化为归档时刻值，不随后续改名或切换变化（现状批次重命名会同步改动该批次所有公示单展示名）。
3. 历史上下文下所有写路径统一短路为「拒绝 + 原因 + 留痕」，覆盖面如下：

| # | 现有覆盖点 | 归档约束 |
|---|---|---|
| 1 | `save()` 全量覆盖唯一键 | 归档副本不进入该全量覆盖路径 |
| 2 | JSON「导入恢复」整包替换 | 须按学年边界校验；禁止覆盖或丢弃归档学年；默认只作用于当前学年上下文 |
| 3 | 「清空示例数据」整包重建 | 只重建当前学年，不动归档副本 |
| 4 | 「重新导入明细」整体替换明细 | 仅当前学年批次可写 |
| 5 | 信息库重置两档（清空字段 / 清空整个名单含结果） | 历史上下文禁用全部重置入口 |
| 6 | 批次重命名同步改动公示单展示名 | 历史学年禁止重命名；归档内展示名固化 |
| 7 | 上游切换级联清空下游版本（旧链路） | 历史上下文禁用；归档副本不受任何切换/级联/回收影响 |
| 8 | 公示单、异议、版本、勘误等全部写路径 | 历史上下文统一拒绝 |
| 9 | 云同步按批次 id 并集 + 较新时间戳覆盖 | 同步边界按学年划分；归档学年不参与常规同步的反向写入；归档迁移走显式独立通道 |

## 3.5 新学年初始化与学年门禁

- 仅继承配置与结构模板：计算权重、各等级/荣誉/专项判定阈值、名额模板、字段口径与公示列配置。
- 业务数据全空：参评名单、附加分明细、名额实例、八层版本、公示单、异议、待办、结果。
- 新学年使用独立 `yearId`；不得通过复制上一学年批次数据的方式创建。
- 学年切换前必须完成上一学年归档或明确停止其写入；不允许两个学年同时处于可写状态。

## 3.6 导出 / 恢复 / 迁移 / 同步边界

- 支持按学年导出为**自包含单一归档文件**（含清单、指纹、结构版本），可在另一环境按学年恢复/迁移；导出文件含学生名单与成绩，属敏感数据，**不得提交仓库**，须被忽略规则覆盖。
- 常规 JSON 备份与归档导出分离，不得混用；「导入恢复」不得跨学年覆盖归档数据。
- 云同步载荷须携带学年边界；归档学年不参与常规同步的反向覆盖；跨设备同步冲突仲裁策略待确认。
- 学生端历年查询优先读归档副本内的已公示结果，**不依赖外部短链是否长期有效**（现状短链本地预览依赖工作 state 中的公示单存在）。

## 3.7 异常场景处理要求

| 场景 | 处理要求 |
|---|---|
| **重复归档（源未变）** | 幂等：以「学年标识 + 源数据指纹 + 归档状态」判定；已归档且指纹一致 → 返回既有归档，不新建、不改写、不重复计数、不重复留痕 |
| **重复归档（源已变）** | 拒绝并告警；更正必须走勘误，不允许静默重归档覆盖 |
| **归档中重复触发** | 返回「进行中」状态，不并发再起一份 |
| **部分失败** | 全成功或全不动：先构建完整副本到暂存 → 完整性校验通过 → 一次性提交；任一步失败则丢弃暂存、学年状态回退「评定中」、当前学年数据**零改动** |
| **失败可见性** | 失败阶段、原因、时间、操作者写入审计并可见提示；**不得静默吞异常**（区别于现有迁移的静默跳过风格） |
| **重试与回滚** | 可基于同一学年标识与新的源指纹重试；启动/恢复时检测到「归档中且无完成留痕」自动回退并标记失败，杜绝僵尸态 |
| **归档期间并发写入 / 中断** | 以「冻结源快照点」为界，过程不读后续写入；若归档中途发生写入导致一致性校验失败，则整体回滚并提示重试；刷新或关闭中断靠幂等键与可恢复状态处理 |
| **归档完成后对源数据的写入** | 一律拒绝；勘误是唯一合法更正途径 |
| **完整性校验不通过** | 阻断归档并列出差异类别，不得提交不完整副本 |

## 3.8 勘误机制

- 勘误为独立于快照的**只追加记录**，引用学年标识与目标对象（批次/层/版本/学号/字段），含原值、更正值、原因、操作者与时间、自身指纹。
- 原始快照**永不改写**；归档指纹在归档时固化、**不因勘误重算**；勘误链单独校验并计入归档元数据独立计数。
- 查询默认展示原始快照，命中对象处**显式标注「存在勘误」**，可展开勘误链，并提供「原始值 / 勘误后」两种视图。
- 勘误不得改变历史结果的可复核性：完整性校验只比对快照指纹与归档时刻记录。

# 四、兼容与风险

**结论**：归档是对快照的封存，与现有评定流程解耦；但单键整包替换、弱指纹、短链外部依赖、容量上限四类约束必须诚实标注，不得写成已具备的保证。

## 4.1 对现有评定流程的影响与兼容要求

| 现有机制 | 兼容要求 |
|---|---|
| 八层评定流水线与逐层「确认门禁」 | 流程、算法、操作习惯、状态文案均不改变；归档只新增学年上下文、归档入口与历史视图 |
| 层内版本留存（版本不可变、引用固化、版本回收保留最近 N 个且保护已确认/已公示/已锁定版本） | 归档含归档时刻全部版本（含试算）；归档前禁止触发版本回收与级联清空；归档副本永不参与回收 |
| 公示管理与公示短链 | 归档不改变已发布短链内容；须定义归档后短链是否长期有效；历史查询不依赖短链 |
| 学生查询页（学号+姓名查本人结果、单公示单） | 现状无跨学年检索；历史查询须绑定归档上下文并强制「仅本人 + 仅已公示」 |
| 异议五态与处理流 | 归档保留全部异议及状态；闭环判定按 3.2 组合口径，不依赖新增终态 |
| 云同步（单 Gist 单文件、按时间戳覆盖） | 学年边界隔离；归档学年不参与常规同步反向写入 |
| JSON 备份 / 导入恢复 | 备份与恢复须带学年边界；归档导出为独立文件，不与常规备份混用 |
| 单键存储 `wb_pjpy_state_v1` | 归档副本不应塞进同一可变键的全量覆盖路径；若引入独立存储，须明确其生命周期、迁移与清理 |
| 存量数据 | 现有批次平滑归入默认当前学年，不得因学年化改造而丢失或不可见 |
| 角色与权限 | 现状仅 `admin`；本方案不要求先落地多角色改造，其它角色权限范围列为待确认 |
| README 版本管理约定 | 本方案为规格文档；后续若实施改 `index.html`，按「一次改动一次提交、可发布节点打标签、shasum 核对、diff 仅在预期范围」执行 |
| 敏感数据不入库 | 归档导出含名单与成绩，一律不得提交；`.gitignore` 模式须覆盖其命名 |

## 4.2 已知限制（诚实标注）

1. 现有 `dataHash` 为纯本地 FNV-1a 32 位指纹，非密码学、无密钥、存在碰撞可能 → 只能证明「与归档时记录一致」，**不能构成抗抵赖的防篡改证明**。本方案承诺的是「完整性校验 + 只读 + 写入拦截 + 全程留痕」；强证明需外部锚定或签名，列为限制与待确认。
2. `version.lock.lockedAt` 无写入实现 → 「结果已锁定」须用归档封存态表达。
3. 异议无「已闭环」终态 → 闭环须组合判定或新增终态。
4. 公示短链本地预览依赖工作 state 中的公示单；归档移出批次可能使本地预览失效，云端短链属外部依赖。
5. 四角色矩阵未落地，实际仅单角色；学生为链接访问者而非应用内登录角色。
6. 浏览器本地存储约 5MB 上限（设计文档自述），多学年全量快照累积会逼近上限。
7. `docs/上下游版本依赖重构设计.md` 属 P0~P6 设计方案、部分未完工；归档方案不得依赖其未完成能力作为前提。

## 4.3 风险登记

| 风险 | 影响 | 缓解要求 | 性质 |
|---|---|---|---|
| 归档副本被保存/导入/清空/同步整包覆盖 | 历史丢失、不可复现 | 全量路径排除 + 双上下文 + 写入拦截 | 阻塞 |
| 前置校验误用 `lock.lockedAt` | 归档永远无法触发 | 按 3.2 重定义口径 | 阻塞 |
| 归档中途写入或中断 | 半成品、快照不一致 | 冻结源 + 原子提交 + 可恢复状态 | 阻塞 |
| 「全量」被版本回收/级联清空削薄 | 试算版本缺失，无法复盘 | 归档前禁止触发，副本永不回收 | 阻塞 |
| 容量耗尽 | 归档失败或写入失败 | 可见告警 + 导出卸载/冷存储路径（阈值待确认） | 可后续 |
| 短链外部依赖失效 | 学生端历年查询不可用 | 归档内保留可解析公示数据，查询走归档上下文 | 可后续 |

# 五、验收标准

**结论**：每条为「操作 → 期望 → 可观察判据」；负向用例必须**被拒绝且留痕**。判据限于状态、指纹、计数、是否被拒、是否有留痕等可判定量，不含主观评价。

| 组 | 编号 | 验收条目 | 通过判据 |
|---|---|---|---|
| 前置校验 | AC-1 | 存在「公示中」公示单时触发归档 | 被阻断，原因含「公示未结束」；无快照生成、学年状态不变 |
| 前置校验 | AC-2 | 存在 待核实 / 已回复未终结 / 采纳-待重算 异议时触发 | 被阻断，逐条列出未闭环异议；无半成品 |
| 前置校验 | AC-3 | 存在 `empty` / `computed` 未确认层时触发 | 被阻断，逐层列出未确认层 |
| 前置校验 | AC-4 | 全部条件满足并完成二次确认 | 状态 `评定中→归档中→已归档`；生成清单与指纹；归档审计完整 |
| 前置校验 | AC-5 | 学年非「评定中」时触发 | 被阻断且说明状态不允许 |
| 隔离 | AC-6 | 归档后对当前学年执行导入明细、两档重置、清空示例、批次改名、版本切换 | 归档副本内容恒定，指纹复算一致 |
| 隔离 | AC-7 | **负向**：用旧备份 JSON 执行「导入恢复」 | 不得覆盖或丢弃归档学年；拒绝或仅作用于当前学年并给出提示 |
| 隔离 | AC-8 | **负向**：尝试修改历史学年任一字段（名单/版本/公示/异议/批次名） | 被拒绝并返回原因；归档指纹不变；尝试被留痕 |
| 隔离 | AC-9 | **负向**：云同步模拟远端含「较新时间戳」的归档学年数据 | 不得反向写历史；同步后归档副本不变 |
| 隔离 | AC-10 | 当前学年连续多次保存 | 归档副本不出现在被覆盖路径，内容恒定 |
| 隔离 | AC-11 | 归档后重命名当前学年批次 | 归档内公示展示名保持归档时刻值 |
| 可见性 | AC-12 | 管理员只读查历史学年 | 可查名单/明细/名额/八层全部版本（含试算）/公示/异议/配置/审计，与归档时刻一致 |
| 可见性 | AC-13 | **负向**：学生端用他人学号+姓名查历年 | 查不到他人数据；仅返回本人已公示结果 |
| 可见性 | AC-14 | 学生端查本人跨两个学年结果 | 返回两条已公示结果，均带学年标识与勘误标注位 |
| 异常 | AC-15 | 同一学年重复触发归档（源未变） | 幂等：不新建、不改写；指纹、清单计数、审计条数均不变 |
| 异常 | AC-16 | **负向**：归档后源数据被写入再触发归档 | 拒绝并告警，不得静默重归档；更正须走勘误 |
| 异常 | AC-17 | 归档中途注入一次写入 / 模拟刷新中断 | 原子回滚：无「已归档」半成品、回到「评定中」、当前学年零改动、失败可见留痕；重试可成功 |
| 异常 | AC-18 | 归档某步骤失败 | 暂存丢弃、失败阶段与原因可查、学年状态回退 |
| 完整性 | AC-19 | 对归档副本做独立回放/复核 | 脱离当前 state 可重放清单计数、各版本指纹、引用链与关键结果，与归档记录一致 |
| 勘误 | AC-20 | 对已归档学年追加勘误后查询 | 原始快照与归档指纹不变；命中处标注「存在勘误」；可切换原始/勘误后视图 |
| 兼容 | AC-21 | 归档后八层评定、确认门禁、公示、学生查询、异议、云同步、JSON 备份按原方式工作 | 现有功能回归通过，无静默失效 |
| 兼容 | AC-22 | 新建下一学年 | 仅含配置模板；名单/明细/版本/公示/异议/待办全空；`yearId` 独立 |
| 兼容 | AC-23 | 尝试把归档导出文件提交仓库 | 被忽略规则拦截；仓库无学生敏感数据 |
| 容量 | AC-24 | 多学年全量快照累积至声明上限 | 归档耗时与占用在声明范围内；逼近上限时有可见告警与导出卸载路径（阈值待确认） |

### B.4 「缺配置」误判的说明（2026-11-11 修复）

**现象**：归档前置校验曾显示「✕ 规则配置与名额已记录（可复盘口径）／缺配置：<批次名列表>」，导致无法归档。

**原因**：`rankWeights(b)`、`gradeRules(b)` 等读取函数自带系统默认值回退（`RANK_W_DEFAULT` = 50/20/15/15、`GRADE_RULES_DEFAULT` = 一二三等奖阈值）；`b.rankWeights` / `b.gradeRules` 字段**只在用户手动点「保存权重」「保存等级规则」「恢复默认」时才写入**。因此字段缺失只代表「正在使用系统默认配置」，不代表「没有规则」。原校验按字段是否存在判定，把从未改过规则的批次（含新建的空批次）误判为缺配置；由于归档按学年整体封存，任一空批次不过即整体阻断。

**修复**：
1. 新增 `effectiveRules(b)`，统一读取「实际生效」的全部规则；校验改为只拦截真正异常的规则（综测权重合计 ≠ 100、等级档位缺失），不再因字段缺失阻断。
2. 归档生成快照时，把每个批次的**生效规则显式固化进快照副本**（不改写工作数据），并在 `manifest.defaultRuleBatches` 记录哪些批次使用默认值；历史结果因此不随日后默认规则调整而失去复盘依据。
3. 归档详情弹窗新增「规则口径（归档时固化）」段落；确认弹窗在规则项下显示「其中 N 个使用系统默认配置，归档时将按生效值固化进快照」。
4. 新增 2 条验证用例：异常权重仍被拦截；3 个批次（含 2 个空批次）全部无显式配置时可正常归档且快照规则完整。

### B.5 数据删除能力（2026-11-11 新增）

> 背景：封存快照原本严格不可变。业务侧需要「删错重来」的兜底通道，故新增**受限删除**：不提供任何局部改写快照的能力，只提供整学年归档删除与工作区批次删除。

| 维度 | 学年归档删除 | 指定批次删除 |
|---|---|---|
| 入口 | 学年与归档面板 → 已归档学年行「删除归档」 | 学年与归档面板 → 当前学年下批次子行「删除批次」 |
| 作用对象 | 归档库 `wb_pjpy_archive_v1` 中的整条学年记录 | 当前可写学年 `state.batches` 中的单个批次 |
| 前置校验 | 管理员角色；归档记录存在 | 管理员角色；批次存在；归属学年存在且**未归档**；该学年至少保留 1 个批次 |
| 二次确认 | 弹窗列明影响范围（批次/参评/明细/版本/试算/公示/异议/勘误/归档时间/指纹），并要求**输入学年名称**后才启用「确认删除」；可先在弹窗内导出备份 | 弹窗列明影响范围（参评/明细/名额/待办/版本/公示/异议）并提示公示中与未终结异议风险 |
| 失败处理 | 归档库写入失败 → 不删除；工作数据保存失败 → 回滚归档记录、学年表、活动指针并提示原因 | 保存失败 → 回滚批次表、活动批次与删除日志；错误经 toast 明示 |
| 一致性处理 | 删除后清理空壳学年实体（避免「已归档但无归档数据」的悬空只读学年）；归档 id 缓存失效；若学年下仍有残留批次，仅清归档标记并把状态复位「评定中」，不误删批次 | 删除活动批次时自动切换到同学年剩余批次；`year.batchIds` 由 `ensureYears()` 同步；清空瞬态计算展示；工具页若正打开则关闭/重渲染 |
| 留痕 | 写入 `state.auditLog`（type=archive，含影响范围与指纹前值），面板展示最近 5 条「删除日志」 | 同左（type=batch，含批次名与各项计数） |
| 接口 | 本项目**无服务端**，删除能力以数据访问层 API 提供：`window.PJPY_DATA_API.deleteArchive(yearId, reason)` | `window.PJPY_DATA_API.deleteBatch(batchId, reason)` |

统一返回结构 `{ok:true, ...}` / `{ok:false, code, msg}`；`code` 取值：`no-permission` / `not-found` / `archived` / `last-batch` / `orphan` / `storage`。页面按钮与后续外部集成都走同一入口，权限在接口层二次校验，不依赖按钮是否渲染。

**已知边界**：① 删除不可恢复，归档删除前建议导出备份；② 已分享出去的公示短链数据存于云端接口，本地删除**不会**回收云端数据，链接仍可能查询到旧公示；③ 审批留痕仅保存在本机 `state.auditLog`，随导入备份整体覆盖，不做异地留存。

**验证**：新增 jsdom 用例 13 条全部通过（权限拒绝、归档删除、记录不存在、批次删除、最后批次保护、归档学年批次保护、写入失败回滚、两类弹窗的二次确认与取消、删除日志展示、接口返回结构、残留批次场景）；原归档回归 36 条与「新建批次命名确认」11 条回归均全通过。

### B.6 修复：「学年无法删除」（2026-11-11）

**现象**：面板「学年与归档」中，当前可写学年（如 2029-2030学年）行只有「工作区可写」徽标，没有任何删除入口；唯一批次点「删除批次」被"学年至少保留 1 个批次"保护拦住 → 学年既不能整体删、也不能靠删批次清空，形成死锁。

**根因（按排除顺序）**：

| 假设 | 结论 | 依据 |
|---|---|---|
| 关联数据约束 | **成立（部分）** | 学年→批次为从属关系，原实现只提供批次粒度删除，缺学年粒度的级联删除通道；`last-batch` 保护使唯一批次删不掉 |
| 权限校验 | 排除 | `ROLES` 仅 `admin` 一种角色，`canDeleteData()` 恒真；接口层无其它角色分支 |
| 状态限制 | 排除 | 可写学年状态为「评定中」，不触发 `isYearArchived` / 归档前置校验分支 |
| 后端逻辑缺陷 | 不适用 | 本项目无服务端，删除逻辑全在数据访问层；上一轮实现本身无缺陷，**缺陷是入口/能力缺口** |
| 接口缺口 | **成立（主因）** | `PJPY_DATA_API` 只有 `deleteArchive` / `deleteBatch`，没有 `deleteYear`；面板渲染只对已归档学年输出「删除归档」、对批次输出「删除批次」，当前学年行无按钮 |

**修复**：

1. 新增数据访问层 `deleteYearData(yearId, reason)`：权限校验 → 级联删除该学年及其全部批次 → 移除学年实体 → **上下文兜底**（若已无可写学年，按"新学年仅继承配置模板"的既有约定自动建立新学年与首个空批次，避免 `activeBatch` 悬空、`B()` 取不到批次导致渲染异常）→ 写删除日志 → 失败整体回滚（学年表/批次表/活动指针/日志）。
2. 新增 `deleteYearModal()` 与面板入口：当前学年行输出「删除学年」按钮；弹窗列影响范围（批次数/参评/明细/待办/版本/试算/公示/异议）、公示中与未终结异议风险、不可撤销提示，并要求**输入学年名称**才启用「确认删除」。
3. `PJPY_DATA_API` 增补 `deleteYear(yearId, reason)`；`last-batch` 与界面提示文案改为引导使用「删除学年」。
4. 两处确认输入框的占位符由"直接显示学年名"改为「请输入「XXX」」，避免被误认为已预填。

**修复后预期行为**：当前学年行出现红色「删除学年」→ 点击弹出影响范围与二次确认弹窗 → 输入学年名称后「确认删除」可点 → 确认后该学年及其批次数据全部清除，自动建立新的可写学年（仅继承配置模板），顶栏学年/批次选择器、批次概况、工具页均可正常使用；取消或名称不匹配时不做任何改动。

**验证**：新增 jsdom 用例 11 条全部通过（权限拒绝、唯一学年删除并重建、非活动学年删除、学年不存在、已归档学年拦截、写入失败整体回滚、面板入口与二次确认、取消不生效、删除后界面与选择器仍可用、接口可用、唯一批次保护文案引导）；既有删除专项 13 条、归档回归 36 条、新建批次 11 条回归全通过；Chrome 无头渲染确认面板按钮与删除弹窗布局正常（影响范围、风险提示、输入确认、禁用态确认按钮）。
